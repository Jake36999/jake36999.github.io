Custom_Agent_Forge

Fine-tunes models — or matures their reasoning on past failures — using cryptographically-audited data for full traceability.

The problem

Fine-tuning well means matching the training approach to what the model actually needs — general reasoning, coding ability, or specifically not repeating a known failure — and being able to prove the training data itself is trustworthy.

The approach

Four modes select both what data gets ingested and what kind of model comes out:

  • Coding Assistant — trained on GitHub repositories via a rolling buffer
  • Scholar — trained on documents and PDFs, weighted toward semantics over structure
  • Project Manager — trained on both, tuned to retain reasoning over code and semantics together, usually paired with system-prompt instructions at deployment
  • Veteran — builds a DAG from a reverse graph of identified failures and their solutions, fine-tuning the model specifically to avoid repeating them

Every accept and reject decision is written to a SHA-256 hash-chained ledger. It's a one-way, project-agnostic pipeline — base model in, fine-tuned model out — not an agent, and not used to support one.

The result

Run against encode/starlette, a real production codebase. The ledger's hash chain verified intact across the full run.

Agent governance

Agent_backend

Problem: letting an agent modify files is a liability without verification and a reliable path back — and most agent backends only work by replacing a client's existing interface rather than fitting into one they already use.

Approach: an agentic backend that plugs into an existing UI. Models can view, create, edit, and delete files under strict control gates: every action logged in human-readable YAML, every patch requiring an explicit approval record and a SHA256 diff match before applying, with snapshot-based rollback. A Python daemon chains multi-step operations into a single response instead of multiple round-trips.

Own suites: 264 Python (12 subtests) + 25 Node contract tests · v0.2.0

Developer tooling

ToolSet

Problem: cloud LLM services have file-upload limits and finite context windows — feeding them a real codebase means hitting the limit or drowning the model's attention in boilerplate.

Approach: one process, several tools — take a repository and compile it into whatever form actually fits the job. Full-directory snapshots when the whole structure matters, AST-based extraction of just the relevant functions when it doesn't, or a repackaged local pipeline for Google Colab's resources. The techniques matured past the original problem: the snapshot/approval/rollback discipline now in Agent_backend, and the semantic code slicing now in Custom_Agent_Forge, both trace back to tooling built here first.

Own regression suite: 289/289 · CI on Windows and Linux

Applied ML / RF

network_management

Problem: device-free presence sensing and network security monitoring are typically separate disciplines with no shared timeline.

Approach: cross-vendor hardware — a Ubiquiti UniFi nanoHD access point and a Mercusys MR30G router bridging two Intel 5300 CSI capture cards — feeding a low-latency ZeroMQ bridge from a secondary capture PC to a GPU-accelerated physics mirror on the main machine (the same messaging approach used in low-latency trading). Correlated with network reconnaissance telemetry into a single SIEM timeline over mTLS, monitorable from any device on the network via a standalone intranet server. Portable to any mesh network with minor modification.

Infrastructure locked and proven (June 2026); classifier in active research
